## Addendum (2026-09-06): what implementation changed

Three things in the original design below did not survive contact. The shape of
the package is unchanged; the mechanism is.

**1. A package default is not a file — it is a Gettext call the caller passes
in.** The original layout gave every package a `priv/phoenix_kit_templates/`
tree, with prose inside the files coming from `gettext/1`. A leaf cannot do
that: evaluating `<%= gettext(…) %>` needs the *sending* package's Gettext
backend in scope, and depending on one would end this package's leaf status —
which is the entire reason it can sit upstream of core.

So `render/4` takes the default as an argument, already localized:

    Templates.render("new_login_alert",
      %{subject: gettext("New login to your account"), text: gettext("Hi …")},
      variables, locale: locale, paths: paths)

This is better than the file-per-locale alternative anyway. A shipped default
kept as seven files forks one sentence seven ways and drifts; as a Gettext call
it rides the extraction pipeline the sending package already runs. **Files are
now purely the host-override mechanism** — and a host writes one or two
languages, not seven, so the forking objection does not apply to them.

**2. Overrides are read at runtime, not compile time.** The original said
compile-time with `@external_resource`. There is no such moment: overrides live
in the *host* application, which compiles separately from this package. They are
read on demand and cached in `:persistent_term` — including the *absence* of a
file, since a missing override is the common case and would otherwise cost a
`File.stat` per send. `reset_cache/1` takes an optional root list so a dev
reload, or an async test, clears only its own entries.

**3. Override files are `.txt` / `.html`, not `.eex`.** Substitution is
`{{variable}}`, not EEx, so an `.eex` extension advertised a templating language
the renderer does not implement.

Both open questions below are answered by the above: discovery is an explicit
`:paths` option (a leaf must not read another application's config), and the
read is at runtime.

## Addendum (2026-10-07): a write API and an optional editor

"No admin UI, no Phoenix" below no longer holds in full. A host that edits its
own override files from an admin screen needed both, and they were added here
rather than to each host:

- **A write API** in `Overrides` (`write/5`, `delete/4`, `delete_template/2`,
  `copy_template/3`, `list/1`) — plain `File` calls on one root, with the read
  path's name and locale rules. It adds no dependency.
- **`PhoenixKit.Templates.Editor`**, a `Phoenix.LiveComponent`. Leaf status is
  kept by construction: `phoenix_live_view` is an **optional** dependency, the
  module is compiled only when the host has it, and it depends on nothing in
  the PhoenixKit tree — no `phoenix_kit`, no Gettext backend, no assets. A host
  without LiveView, `phoenix_kit` included, pulls in nothing new.

That still widens the package past "a pure renderer", which is what "The cost
this buys" below warns about. If the maintainers would rather keep UI out, the
component moves to the host application and the write API stays here.

## What this package is

A **pure renderer** for message templates: resolve a named template for a
recipient's locale across an override chain, substitute `{{variables}}`,
return the parts. Email, push, Telegram, SMS and the in-app inbox all consume
the same thing.

What it is *not*: no database, no schema, no admin UI, no Ecto, no Phoenix, no
gettext backend of its own. Templates are files owned by the package that
sends the message; translation happens in that package's gettext. This one
resolves and substitutes.

That is what makes it a **leaf**: it depends on nothing in the PhoenixKit
tree, so `phoenix_kit` can depend on *it* without a cycle. Feature modules
reach it transitively through core.

### The cost this buys, stated plainly

Core's release becomes gated on a release here, and modules pinning core
`~> 2.0` carry the pin transitively. That is a real coordination cost on
every core release, accepted deliberately in exchange for a small repo with a
fast precommit that can be refactored without touching core. It is only worth
it if this package stays small and stops changing — if it starts accreting
storage or UI, the trade has gone bad and it should fold back into core.

## Resolution chain

```
1. host priv/   · recipient locale
2. host priv/   · "en"
3. package      · recipient locale   (gettext)
4. package      · "en"
5. literal
```

The host layer is the customization story that replaces the admin editor:
a host drops a file into its own repo, version-controlled and reviewable,
and it wins over the package default. It requires a developer and a deploy.

The package layer is the translated baseline. It ships filled in for all
seven locales through the existing gettext pipeline — unlike the DB model it
replaces, where `wrap_i18n/1` produced `%{"en" => v}` and every install
started English.

Step 5 exists so a caller is never left with nothing.

## File layout

Package defaults live with the package that sends the message:

```
<root>/<name>/<part>.<locale>.<ext>     text.en-GB.txt
<root>/<name>/<part>.<ext>              text.txt
```

`subject` and `text` are `.txt`; `html` is `.html`. A root is typically
`Application.app_dir(:my_app, "priv/phoenix_kit_templates")`.

Lookup is most- to least-specific and stops at the first hit —
`text.en-GB.txt` → `text.en.txt` → `text.txt` — so a single-language host
writes one file and is done, while a host that translates its overrides gets
dialect precision. Earlier roots shadow later ones.

Read at runtime and cached (see the addendum): the host app compiles separately
from this package, so there is no compile-time moment at which its files exist
to be read.

This layout also dissolves an existing coupling: `phoenix_kit_emails`
currently hardcodes `billing_invoice`, `billing_receipt`,
`billing_credit_note` and `billing_payment_confirmation` in its
`seed_system_templates/0`. Under this model each package ships its own
defaults in its own repo, and no package knows another's content.

## Content parts

Three parts, named channel-neutrally rather than email-specifically:

| Part | Email | Push | Telegram / SMS | Inbox |
|---|---|---|---|---|
| `subject` | subject line | title | — | — |
| `text` | plain body | body | body | body |
| `html` | rich body | — | — | — |

No generic `parts` map until a channel actually needs a fourth. The existing
`PhoenixKit.Notifications.Channel` envelope (`%{icon, title, text, url,
locale}`) is already this shape, which is the good sign that three is right.

`html` is genuinely optional, not nominally so: **core's own auth emails ship
text-only** — confirmation, reset, magic link, login alert. They are short
transactional messages where plain text wins on the merits (no image blocking,
no dark-mode breakage, no client-specific CSS, better deliverability). A
template directory with no `html.eex` is the normal case, not a stub.

## Chrome is a layer, and core owns it

Today every HTML template carries its own copy of the header and footer —
`phoenix_kit_emails/lib/.../templates.ex:1512`, `:1705`, `:1897`, each with a
different gradient, each redefining `.footer`. Roughly 2,000 lines of inline
HTML, no shared layout anywhere.

Moving to per-package files would make that worse, spreading the duplication
across repos. So chrome is explicit and shared:

- A layout lives in **core**, at `priv/phoenix_kit_templates/_layout/`, fed by
  the branding settings that already exist.
- A template **opts in**. Billing invoices do. Core's auth emails do not.
- It lives in core rather than here because chrome needs branding settings,
  and reaching for those would cost this package its leaf status. This
  package renders the layout it is handed; it does not source it.

## Translation granularity

The template file is **structure**; the prose inside it is `gettext/1`.

Do not make an HTML body a single msgid. It is an unusable translation unit,
and any markup tweak invalidates all seven locales at once. Keep the HTML
skeleton — layout, button, footer — as untranslated structure, and gettext
only the short prose fragments inside it.

Hard constraint carried from the `admin_panel_label` work: a msgid must be a
**literal** `gettext/1` call, or extraction silently misses it and the string
ships untranslated. This has bitten before.

## Public API sketch

```elixir
PhoenixKit.Templates.render(name, defaults, variables \\ %{}, opts \\ [])
#=> %{subject: String.t() | nil, text: String.t() | nil, html: String.t() | nil}

PhoenixKit.Templates.missing_variables(name, defaults, variables \\ %{}, opts \\ [])
#=> %{optional(:subject | :text | :html) => [String.t()]}
```

`defaults` is the package's own content, already localized by the caller.
`opts` carries `:locale` and `:paths` (host override roots, tried in order).

Substitution is `{{variable}}` with optional inner whitespace, matching what the
DB templates used so exported content carries over unchanged; atom and string
keys are both accepted.

An **unbound placeholder is left verbatim and never raises**. Both blanking and
raising are worse: a silent empty string reads as finished copy and ships, and a
message with one flawed line still beats a message that never arrives. A caller
that wants it to be an error asks `missing_variables/4` first.

`name` and `locale` are validated against strict patterns before being joined
onto a root — this module turns a caller-supplied name into a filesystem read,
which is not a boundary to leave to the caller.

## What this replaces

In `phoenix_kit_emails`, deleted outright:

- `Templates.seed_system_templates/0` and `wrap_i18n/1` — nothing to seed
  when defaults are files. This removes the bug class behind commit
  `366c6254 "Fix email template seeding failing on fresh install"`.
- `web/templates.ex`, `web/templates.html.heex`, `web/template_editor.ex`,
  `web/template_editor.html.heex`, plus the route and settings tab.
- `Template` schema and `Templates` context, once the table is gone.

In core, the five hardcoded fallbacks in `user_notifier.ex` (`:108`, `:147`,
`:186`, `:256`, `:307`) are **deleted, not ported**. Because this package is a
hard dependency of core and template files ship in each sending package's own
`priv/`, core's templates are always present — there is no degraded mode left
to write. That holds only while the dependency stays hard; an optional dep
would reintroduce the feature-detection indirection this design removed.

In core's `PhoenixKit.Email.Provider`, four callbacks lose their reason to
exist once lookup is a compile-time filesystem read:

| Callback | Fate |
|---|---|
| `get_active_template_by_name/1` | removed — resolution is not provider business |
| `render_template/2`, `/3` | removed — `PhoenixKit.Templates.render/3` |
| `track_usage/1` | removed with `usage_count` / `last_used_at`; derive from `phoenix_kit_email_logs` if the metric is wanted back |
| `get_source_module/1` | removed — the owning package is known statically |

`status: "draft"/"active"` disappears: a file that exists is active.
Interception, `maybe_enqueue/2`, AWS config and provider detection are
untouched — those are delivery concerns and stay in the emails package.

## Migration

The destructive part. Installs have rows in `phoenix_kit_email_templates`,
and some are operator edits that must not be clobbered.

1. **Classify, don't clobber.** For each row, compare against what the old
   `seed_system_templates/0` would have produced. Byte-identical → untouched
   seed, safe to drop. Different → a real customization.
2. **`mix phoenix_kit.templates.export`** writes each customized row into the
   host's `priv/phoenix_kit_templates/` for the operator to review and commit.
   This is the entire upgrade path, and it must ship **and be announced** at
   least one release before anything drops.
3. **Operator-authored rows** (`is_system: false`, newsletter layouts) are not
   exported — they migrate into a newsletters-owned table. See the core doc's
   scope-correction section for why these cannot become files.
4. **Then** core drops `fk_newsletters_broadcasts_template` and hands the table
   over, per the transitional note in
   `phoenix_kit_emails/dev_docs/reports/2026-08-12-emails-table-adoption.md`.

Ordering is forced: core's chain runs before every module chain, so the core
FK drop and the newsletters table creation must land in the **same release**,
and the export task must predate both.

## Sequencing (across repos)

| # | Work | Repo | Risk |
|---|---|---|---|
| 1 | Locale resolver threaded through the five `user_notifier.ex` sites | core | none |
| 2 | gettext the hardcoded fallbacks + `Notifications.Render` literals | core | none |
| 3 | This package: renderer, resolution chain, file layout | here | none |
| 4 | Missing templates as files: `new_login_alert`, `magic_link_registration` — plus the "review your sessions" link the alert currently lacks | core | none |
| 5 | Export task, released and announced | emails | none |
| 6 | Table split: newsletters takes the operator-authored rows, core drops the FK, emails loses editor + seed | 3 repos | **irreversible** |
| 7 | Notification channels render through this package | core | low |

Steps 1–2 are worth doing regardless of whether the rest happens; they change
the mail that actually lands in an inbox today. Step 6 is the only one that
cannot be walked back.

Step 7 is the payoff beyond email: `Channel`'s envelope `:locale` is
documented today as *"a hint, not a guarantee the `:text` is already
translated"*. It becomes a guarantee.

## Open questions

- ~~**Host override discovery**~~ — settled: an explicit `:paths` option. A leaf
  package must not read another application's configuration, so the *caller*
  resolves roots (from `config :phoenix_kit, template_paths:` or a default) and
  passes them down. This also composes with umbrella hosts and lets a host keep
  templates outside `priv/`.
- **Package naming** — `phoenix_kit_templates` describes it, but this package
  never stores a template. `phoenix_kit_template_renderer` is uglier and more
  honest. Decide before the first publish; renaming a Hex package is painful.
- **Read-only viewer** — operators lose all visibility into what the system
  sends them. A non-editable "here is what this email looks like" admin page,
  salvaged from the editor's preview code, may be worth keeping in core.
- **Does this stay a package?** Revisit after step 3. If it lands at a few
  hundred lines of pure functions and then sits still, the trade holds. If it
  is still churning when step 6 arrives, fold it into core and drop the
  release-ordering constraint.
